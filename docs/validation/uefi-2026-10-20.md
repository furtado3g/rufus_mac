control using the original ISO behaved the same way. Five Linux distributions
also passed extraction, mount and `fsck`; Fedora reached Anaconda and Alpine

## Commands

Extraction image, attached as a USB mass-storage device:

```console
$ cp /opt/local/share/qemu/edk2-i386-vars.fd /tmp/ovmf-vars.fd
$ /opt/local/bin/qemu-system-x86_64 \
    -name image2usb-uefi-test \
    -machine q35,accel=hvf \
    -cpu host -m 4096 -smp 4 \
    -drive if=pflash,format=raw,readonly=on,file=/opt/local/share/qemu/edk2-x86_64-code.fd \
    -drive if=pflash,format=raw,file=/tmp/ovmf-vars.fd \
    -drive if=none,id=usb,format=raw,snapshot=on,file=/tmp/real-extract.img \
    -device qemu-xhci -device usb-storage,drive=usb,bootindex=0 \
    -vga std -display vnc=127.0.0.1:1 \
    -serial file:/tmp/qemu-serial.log \
    -qmp unix:/tmp/qemu-qmp.sock,server=on,wait=off
```

DD-mode control, using the original ISO as USB storage:

```console
$ cp /opt/local/share/qemu/edk2-i386-vars.fd /tmp/ovmf-vars-iso.fd
$ /opt/local/bin/qemu-system-x86_64 \
    -name image2usb-dd-control \
    -machine q35,accel=hvf \
    -cpu host -m 4096 -smp 4 \
    -drive if=pflash,format=raw,readonly=on,file=/opt/local/share/qemu/edk2-x86_64-code.fd \
    -drive if=pflash,format=raw,file=/tmp/ovmf-vars-iso.fd \
    -drive if=none,id=iso,format=raw,snapshot=on,file=/Users/lfurtado/Downloads/DESERT_5.5.2_26.04_LTS_amd64.iso \
    -device qemu-xhci -device usb-storage,drive=iso,bootindex=0 \
    -vga std -display vnc=127.0.0.1:2 \
    -serial file:/tmp/qemu-dd-serial.log \
    -qmp unix:/tmp/qemu-dd-qmp.sock,server=on,wait=off
```

`snapshot=on` keeps QEMU from modifying the image.

## Observations

OVMF enumerated the USB device and started it directly:

```text
BdsDxe: loading Boot0001 "UEFI QEMU QEMU USB HARDDRIVE 1-0000:00:03.0-1" from PciRoot(0x0)/Pci(0x3,0x0)/USB(0x0,0x0)
BdsDxe: starting Boot0001 "UEFI QEMU QEMU USB HARDDRIVE 1-0000:00:03.0-1" from PciRoot(0x0)/Pci(0x3,0x0)/USB(0x0,0x0)
```

The extracted image showed the ISO's GRUB menu (including "Try and Install
DESERT OS Linux") and then booted `/casper/vmlinuz` and `/casper/initrd.gz` from
the FAT32 partition. The live desktop, installer icon and dock appeared after
roughly one minute.

Both the extracted image and the DD control print this non-fatal line on the
serial console before the menu:

```text
error: symbol `efi_wrap_10' not found.
```

The two serial logs are byte-identical. This is a GRUB/module mismatch inside
the ISO (most likely a video module such as `efi_gop`/`efi_uga`) or a QEMU/OVMF
quirk, not an extraction regression: the DD control reproduces it, and both
paths reach the live desktop. It should be tracked as a cosmetic warning.

## Follow-ups

- Repeat on physical UEFI hardware; QEMU/OVMF is necessary but not sufficient.
- Repeat on Linux with KVM/OVMF and on Windows with QEMU/OVMF.
- Add the CI smoke test with a kernel banner on the serial console. This ISO
  uses the graphical console for the kernel, so CI needs `console=ttyS0` or a
  distro that prints to serial by default.
- MBR partition type `0x0C` worked with OVMF; no `0xEF` fallback was needed for
  this image. Keep `0x0C` unless a firmware test shows otherwise.
